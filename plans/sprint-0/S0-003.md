# S0-003 - Settings

## Summary

Implement the typed environment contract used by the FastAPI application, database, Redis, authentication, email, and later provider adapters.

## Sprint Context

- Area: Platform / Configuration
- Priority: P0
- Depends On: S0-001,S0-002
- Source: `roadmap/EKUMIDAYOMI-BACKEND-ROADMAP.md`
- Change specification: `changes/sprint-0/changes-s0-003-settings.md`

## Step-by-Step Implementation Plan

1. Create `core/config.py` with a Pydantic `BaseSettings` subclass and UTF-8 `.env` support.
2. Define environment, API metadata, PostgreSQL, Redis, host, origin, cookie, session, rate-limit, SMTP, and bootstrap settings.
3. Use secret-aware field types for credentials where practical.
4. Parse comma-separated values deterministically and remove blank entries.
5. Add an `active_database_url` property that requires a dedicated test URL in test mode.
6. Add production-mode validation for debug, docs exposure, wildcard network policy, secure cookies, and placeholder values.
7. Expose FastAPI initialization values without leaking infrastructure credentials.
8. Add a cached default settings accessor and a clear test override pattern.
9. Write focused unit tests for successful and rejected configurations.
10. Document which settings are required immediately and which remain optional until later provider sprints.

## Scope Decisions and Discrepancies

- Payment, shipping, object-storage, and external analytics credentials should have reserved documentation but need not be required before their provider is selected.
- Local HTTP development may use an insecure cookie only when `APP_ENV=development`; production must require `Secure`.
- Interactive API documentation may remain enabled in development and test but should require an explicit production decision.

## Acceptance Criteria

- Application configuration is loaded through one typed module.
- `APP_ENV=test` fails without a dedicated test database URL.
- Unsafe production defaults are rejected at settings validation time.
- Host and origin lists parse consistently.
- Secret values do not appear in settings representations or test output.
- Unit tests cover all environment branches.

## Done When

- Later infrastructure can consume one validated settings object without direct environment reads.
